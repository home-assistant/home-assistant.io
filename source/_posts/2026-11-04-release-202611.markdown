## Welcome to the Marketplace

For years, the community has built {% term "custom integrations" %}, dashboard cards, themes, and templates for Home Assistant. People found them through HACS, the Home Assistant Community Store. With this release, HACS becomes part of Home Assistant as the new [Marketplace](/integrations/marketplace/).

The Marketplace brings the existing HACS experience into Home Assistant and the regular release process. It works with every installation type, including {% term "Home Assistant Container" %}, without manually downloading or unpacking files. Everything in the Marketplace is free, and that will not change.

### Browse and install

You can find the Marketplace under **Settings** > **Marketplace**. It comes with Home Assistant, so there is nothing to set up. As an administrator, you can browse the catalog and install integrations, dashboard cards, themes, and templates. You do not need a GitHub account to install or update projects.

<img src='/images/blog/2026-11/marketplace-settings.png' alt='Screenshot of the Home Assistant settings page, with a new Marketplace item between Apps and Dashboards, described as: Install integrations, dashboard cards, themes, and templates shared by the community.' class='no-shadow' />

Installing a new {% term integration %} got shorter, too. In HACS, you downloaded it, restarted Home Assistant, went to **Devices & services**, and searched for it again to set it up. In the Marketplace, you select **Install**, and you land straight in its setup flow, without a restart. Updates still need a restart for now.

The page of each project now shows more than its README: how often it was downloaded, its stars on GitHub, and the Home Assistant version it requires, so you know what you're getting into before you install.

<img src='/images/blog/2026-11/marketplace-project.png' alt='Screenshot of the Marketplace page of the Spook integration, installed and ready to set up, with a notice that it is made by the community, and its required Home Assistant version, last change, downloads, stars on GitHub, and open issues.' class='no-shadow' />

Every project you install gets an {% term update "update entity" %}, so updates show up under **Settings** > **Updates**, next to the updates of Home Assistant itself. After an update, a repair tells you when a restart is needed, and can restart Home Assistant for you.

The first time you open the Marketplace, it shows a notice. Everything in the Marketplace is made by the community. It is not tested, audited, or supported by the Home Assistant project, and it runs inside your Home Assistant. Read the notice, select **I understand the risks and agree**, and you're in. Browsing works before that. Installing and updating does not.

<img src='/images/blog/2026-11/marketplace-warning.png' alt='Screenshot of the Marketplace notice, titled Before you install from the Marketplace. It explains that anything you install can connect to the internet, share your data, or slow down Home Assistant, followed by three tips and an I understand the risks and agree checkbox.' class='no-shadow' />

The Marketplace adds several improvements:

- Group the **Browse** and **Installed** lists by status, type, or source. Home Assistant remembers your grouping.
- Filter by source to distinguish the community catalog from custom repositories.
- Select multiple repositories on the **Installed** tab and uninstall them at once.
- Skipped updates no longer keep a repository at the top of the list or count in the update badge. A new release makes the update available again.
- Search, filters, and sorting are saved in the URL, so you can share a link to a specific Marketplace view.
- Integrations show their brand images before you install them.

<img src='/images/blog/2026-11/marketplace-group-by.png' alt='Screenshot of the Marketplace Browse tab, grouped by status into Installed and New, with the Group by menu open showing Status, Type, Source, and Don&#39;t group.' class='no-shadow' />

### Custom repositories

Not every project is in the catalog. To add one that is missing, select **Add from link** and enter its repository URL. The Marketplace then lists it with your other repositories.

The **Custom repositories** page lists repositories you added this way and lets you open or remove them. A repository stays in the list until you uninstall it.

Custom repositories require a GitHub connection. The Marketplace uses GitHub device sign-in, so you approve the connection on GitHub without entering your password in Home Assistant. The connection only reads public information and cannot access private repositories.

### Where your downloads come from

By default, the Marketplace gets its catalog and everything you install from GitHub. Where GitHub cannot be reached, such as in mainland China, you can switch to the mirrors run by the Home Assistant China community. Go to **Settings** > **Marketplace**, select the three dots {% icon "mdi:dots-vertical" %} menu in the upper-right corner, and select **Download source**. If the Marketplace cannot reach the catalog and a mirror is available for your country, a repair suggests it.

Everything the Marketplace downloads then goes through whoever runs that mirror, and through a third-party proxy whenever those mirrors cannot be reached: the catalog, and the code you install. Only pick a download source you trust. If you used the Chinese version of HACS, the Marketplace selects these mirrors for you when it migrates.

Thanks, [@frenck]!

### Thank you, HACS

HACS made this possible. [@ludeeus] founded it and donated it to the Open Home Foundation about a year and a half ago, which is what made bringing it into Home Assistant possible. Together with the HACS maintainers and the many developers publishing their projects, he built the ecosystem that the Marketplace now carries forward. Thank you. ❤️

If you use HACS today, there is nothing you need to do. Home Assistant migrates it when it starts after the update. Everything you installed stays installed and keeps receiving updates, your custom repositories and update entities carry over, and links and bookmarks that point to HACS now open the Marketplace.

The HACS installer stops at Home Assistant 2026.11, so a separate HACS installation is no longer possible on this version. The old HACS won't get new releases either: the Marketplace ships with every Home Assistant update. Everything you need to know about the move, for users and for publishers, is in the [Marketplace documentation](/integrations/marketplace/#coming-from-hacs).

This is a starting point, and the first version of what a marketplace for Home Assistant could become. Got ideas? Share them in the Marketplace section of the [feature request discussions](https://github.com/orgs/home-assistant/discussions) on GitHub. Found a bug? Report it in the Home Assistant issue tracker, not in the HACS repository.

## Exclude items from a target

Targets are a great way to keep your {% term automations %} and {% term scripts %} up to date. Point one at an {% term area %}, a {% term floor %}, or a {% term label %}, and Home Assistant finds the matching {% term entities %} for you, including the ones you add later. There was just one catch: you couldn't leave one out. Turn on all the lights on the ground floor, except the one in the kitchen? Your only option was to list every light yourself, and lose everything that made the target smart in the first place.

You can now exclude entities, {% term devices %}, areas, floors, and labels from a target. In a {% term trigger %}, {% term condition %}, or {% term action %}, select **Exclude target** next to **Add target**, then choose what to leave out. You can also open a target's details, clear the checkboxes of the items to exclude, and select **Apply**.

<img src='/images/blog/2026-11/exclude-target-details.png' alt='Screenshot of the target details of the Ground floor, with checkboxes to include or exclude each area, device, and entity. The Laundry room and its ceiling light are struck through, and the light is marked as excluded by the Laundry room.' class='no-shadow' />

Each exclusion is listed below the targets it takes entities out of, with the number of entities it removes. An exclusion that doesn't match anything has no effect, and is listed under **Exclusions with no effect**, where you can remove it.

And exclusions stay as smart as the targets they belong to. Home Assistant works them out every time the trigger, condition, or action runs. Exclude the kitchen, add another light to the kitchen next month, and that light is left out as well. No need to touch the automation again.

This works in triggers, conditions, and actions, in both automations and scripts. If you write {% term YAML %}, add an `exclude` block to the `target`, with the same keys as the target itself. For all the details, including how old-style {% term groups %} behave, refer to [excluding targets](/docs/automation/targets/#excluding-targets).

Thanks, [@jpbede], [@emontnemery], and [@marcinbauer-ohf]! 🙏

The automation editor also has a few improvements:

- **Replace a step**: Changed your mind about a {% term trigger %}, {% term condition %}, or {% term action %}? Select **Replace** in its menu to swap it for another one in the same place. Home Assistant keeps the settings the new item accepts, so you don't have to pick the target and fill in the options again. It works in the script editor as well. Thanks, [@nielsrowinbik]!
- **Is not for the state trigger**: Set **From** or **To** to **Is not** to make a {% term trigger %} fire when the state changes to or from any value other than the one you select. No YAML is needed. Thanks, [@Skaronator]!
- **Recently used**: The dialog for adding a trigger, condition, or action now starts with the ones you used recently, including your recently selected targets. Thanks, [@wendevlin]!
- **People in the target picker**: When adding a trigger or condition, find **People** under **Other**, next to **Time** and **Sun**. This makes it easier to create a rule for when someone comes home. Thanks, [@marcinbauer-ohf]!
- **Edit ID is back**: You can set the ID of a trigger from its menu again. Thanks, [@jpbede]!
- **Edit in YAML for choose options**: Edit the options of a choose action in YAML, like other rows. Thanks, [@oneseventhree]!
- **Undo after cutting**: If you cut a trigger, condition, or action by mistake, select **Undo** in the notification to restore it. Thanks, [@marcinbauer-ohf]!

## Sections that fill themselves

A dashboard section is usually a list of cards you put together by hand. Add a new light to the living room, and you have to remember to add its card too. Automatic sections take care of that for you: they pick their cards themselves, and stay up to date when you add or remove {% term devices %} and {% term entities %}.

When you create a section, Home Assistant now asks what you want: a manual section you fill card by card, an automatic section, or the section you just copied. Pick **Automatic section**, and you get the list of automatic sections, each with a live preview, so you see what you get before adding it.

<p class='img'><img class='no-shadow' src='/images/blog/2026-11/automatic-section-picker.png' alt='Screenshot of the Choose an automatic section dialog, with live previews of the Common controls, Device, and Entities sections.'/>Pick an automatic section, and see what it looks like before adding it.</p>

**Common controls** shows the entities you use the most, just like on the **Overview** dashboard. Next to it, two automatic sections are new in this release. The **Device** section shows the entities of one {% term device %}, as tiles or in a single entities card, grouped by category, with the device name, its {% term area %}, and its battery level in the heading. The **Entities** section shows every {% term entity %} of the types you pick, like all your lights or all your batteries, in the areas, floors, devices, or labels you choose. Add a light to the ground floor, and it shows up in your ground floor lights section on its own. If you installed sections made by the community, they are listed too, under **Community sections**.

<p class='img'><img class='no-shadow' src='/images/blog/2026-11/entities-section-editor.png' alt='Screenshot of the Entities section editor, set to show lights on the First floor, with the Key Light Mini excluded, next to a preview of the lights grouped by area.'/>Pick the types of entities and the targets, and the section shows every match.</p>

You can also start from the device. On its device page, select **Add to…** > **Add to a dashboard**, and pick a dashboard and a view. In a sections view, you get a **Device** section for that device. In other views, you get an **Entities** card, and you choose which categories of entities to include. This replaces the **Add to dashboard** buttons at the bottom of each list of entities on the device page.

## Name it once, Home Assistant adds the context

Name a thing once, and Home Assistant makes sure it makes sense everywhere. That is the idea behind how {% term entities %} are named from this release on, and it has been more than four years in the making. You give an entity its own name, like "Temperature". Home Assistant knows which {% term device %} it belongs to, and in which {% term area %} that device lives, so it can add that context where it helps. By default, that is the name of the device: the "Temperature" of a "Thermostat" in the "Bedroom" shows up as "Thermostat Temperature". Where you want more, a card can add the area too, like "Bedroom Thermostat Temperature".

Naming has been a topic in the community for years, with threads like "How do you name your devices?" and "Naming strategies for entities?", all looking for a system that keeps a growing home readable.

It's time to let those systems go. You shouldn't need a strategy to make sense of the information in Home Assistant. Home Assistant should give you the context you need, at the moment you need it. Now you rename the device, and every entity on it follows. Entities you renamed, and entities you never touched, get their context the same way.

You see this in dashboards, settings, the activity and logbook, the voice assistant settings, and the apps. The same name, in the same structure, everywhere you look.

A few things to know:

- **Renaming an entity** only renames the entity. If you want to change the name of the device, rename the device. If an entity represents the main function of its device, turn on **Main entity of the device** in its settings, and it goes by the name and the area of the device.
- **Devices with multiple parts**, like a power strip, now get a {% term device %} per part, each with its own name and {% term area %}. These are called child devices. A child device inherits the area of its parent, until you give it one of its own. Integrations are moving to them one by one, starting with the multi-channel switches in Tuya.
- **Your own names are kept.** Home Assistant migrates names you set. If an entity's displayed name changes, the old name remains an alias for voice assistants. For example, "turn on the ceiling light" continues to work.
- **Templates:** The `friendly_name` attribute is planned for deprecation. Use [`entity_name()`](/template-functions/entity_name/), [`device_name()`](/template-functions/device_name/), and [`area_name()`](/template-functions/area_name/) to build the name you need.

What doesn't change: entity IDs. Your {% term automations %}, {% term scripts %}, and dashboards keep working.

We are upfront about one thing: this is a backward-incompatible change. Some names look different after the update, and you notice that most on your dashboards. Cards, badges, and rows without a name now show the device name followed by the entity name, instead of the friendly name. Making them shorter is quick: rename the device or the entity, turn on **Main entity of the device** for the entity that represents the device, or set a name on the card. The details are in the [backward-incompatible changes](#backward-incompatible-changes) below.

This is the short version. [A separate blog post](/blog/2026/11/03/naming-things-in-home-assistant/) about entity naming tells the full story.

This project ran for more than four years, and many people worked on it along the way. Thank you to everyone who helped make this happen! 🙏

## Forms that ask only what they need

Setting up an {% term integration %} sometimes meant reading past options that had nothing to do with your choices. A field can now appear only when another field has a certain value, so a form asks what is relevant and leaves out the rest. While a field is hidden, it isn't required, and its value isn't saved.

You can already see it in the integrations for AI conversation agents, where the settings you rarely touch stay out of the way until you ask for them.

The same works for a {% term blueprint %}. An input, or a whole group of inputs, can depend on the answers you gave earlier, so a blueprint only asks what still applies.

Thanks, [@piitaya]!

## From power to energy in one step

The Energy dashboard works with energy in kilowatt-hours, but plenty of {% term devices %} only report power in watts. A device like that could not be added directly: first you had to set up a {% term sensor %} that adds the power up over time, then come back and add the device.

Home Assistant now offers to do that for you. Add an individual device, a solar panel, or your home consumption with only a power sensor, and when you save, Home Assistant offers to derive the energy sensor from it, or to reuse one you derived from the same sensor earlier. Gas and water work the same way: pick a sensor that reports a flow rate, and Home Assistant offers to derive the total from it.

Thanks, [@MindFreeze]!

## Why did that happen?

A light turned on, and nobody touched it. Or an {% term automation %} did something you didn't expect. Finding out why is part of living with a smart home, so this release adds a handful of ways to find the answer faster.

### See what triggered it

The **Activity** panel has a new **Triggered by** filter. Use it to show only what a person did, what your {% term automations %} or {% term scripts %} did, or what an {% term integration %} did, like HomeKit or Google Assistant. Accounts that don't belong to a person, like the one used by Node-RED, count as integrations. Entries without a known cause are listed under **Other**.

Thanks, [@piitaya]!

### Follow a trace into the script it called

When an {% term automation %} or {% term script %} runs another script, or triggers an automation, the step in its trace now has a **View trace of** link to exactly that run. Before, you had to find the right run yourself, by timestamp. It works from automation to script, script to script, and automation to automation, for each iteration of a repeat, and for a script that starts itself. The link shows up in the step details and in the trace timeline. The page also keeps the run you are looking at in its address, so going back in your browser takes you back to the previous run.

<img src='/images/blog/2026-11/trace-link.png' alt='Screenshot of the trace of the Good night script, with the step details of an action that runs the Turn off downstairs lights script, and a link: View trace of Turn off downstairs lights.' class='no-shadow' />

Thanks, [@Xyolyp]!

### Live logs for each integration

While debug logging is enabled for an {% term integration %}, the banner on its page now has a **Show logs** button, next to **Disable**. It opens a dialog with only the log lines of that integration, including the libraries it uses: first what it logged since Home Assistant started, then new lines as they come in. You can search, turn line wrapping on or off, and download what you captured. Handy while you're trying to reproduce an issue, without digging through the full log.

## Store backups and media on local drives

{% term backups "Backups" %} and media take up a lot of space, and the best place for them is often not the drive Home Assistant runs on. Besides network storage, you can now add an internal drive or a USB drive. Use it for backups, media, or shared files, just like network storage. ## Reach the far corners with LoRaWAN

<abbr title="Long Range Wide Area Network">LoRaWAN</abbr> is a long-range, low-power wireless protocol, often used for battery-powered sensors in places your Wi-Fi never reaches, like a garden, a shed, or a field. Home Assistant now speaks it. Connect your LoRaWAN network server, [ChirpStack](/integrations/chirpstack/) or [The Things Network](/integrations/thethingsnetwork_lorawan/), and Home Assistant offers the matching device {% term integration %}, like [SenseCAP](/integrations/sensecap_lorawan/), when a supported device shows up.

All of it comes together in a new **LoRaWAN** page in **Settings** > **Connectivity**. It shows your connections and how many {% term devices %} each has, and a table of all your devices that you can search and filter by connection. A map shows how your network hangs together: which gateways receive which devices, and which devices no gateway has seen. On the page of a device, you find its radio details, like signal strength, the last time it reported in, and its battery. A device that Home Assistant doesn't support yet still shows up, with a note on what is missing. And when you want to add a new device, Home Assistant takes you straight to the management console of its connection.

## Batteryless switches with Zigbee Green Power

[Zigbee Home Automation](/integrations/zha/) now supports Zigbee Green Power. Green Power {% term devices %} run without a battery: a wall switch powered by the energy of your press, or a sensor that lives off the light in the room. Friends of Hue switches are the best-known example. Until now, Home Assistant passed them by.

They work differently from other Zigbee devices, and the interface follows along. A Green Power device lists its **Source ID** with its network details, and the options that don't apply to it, like reconfiguring it or managing its clusters, are left out. ## Other noteworthy changes

There is even more packed into this release. Here are some of the other changes worth a mention:

- **Keep an eye on radon.** Radon now has its own {% term triggers %} and {% term condition %}, so you can, for example, turn on a basement fan when [radon levels rise](/triggers/air_quality.radon_crossed_threshold/), or [check the radon level](/conditions/air_quality.is_radon_value/) before running an {% term automation %}. Thanks, [@abmantis]!
- **Act after an update.** A new {% term trigger %} starts an {% term automation %} once Home Assistant has started after an update, and tells you which version you updated from and to. It doesn't fire on a normal restart. Thanks, [@frenck]!
- **Expose many entities at once.** Select the {% term entities %} you want in the table under {% my entities title="**Settings** > **Devices & services** > **Entities**" %}, then choose **Expose to voice assistant**, or **Stop exposing to voice assistant**, from the selection menu. Looking each one up separately in the expose dialog is no longer needed. Thanks, [@jpbede]!
- **Switch to YAML with the keyboard.** Press Ctrl + Shift + Y, or Cmd + Shift + Y on a Mac, to move between the visual editor and the {% term YAML %} editor. It works in the automation, script, and scene editors, in card and dashboard editors, and in **Settings** > **Tools** > **Actions**. You can find it in the keyboard shortcuts dialog, under **Other**. Thanks, [@Jump-333]!
- **Drag picture elements into place.** In the Picture elements card editor, select an element in the preview and drag it where you want it, instead of working out its coordinates. Thanks, [@RaHehl]!
- **Combine calendars into one.** Create a calendar group with the [Group] integration, and it shows the events of all its member [calendars][Calendar] together. Thanks, [@elupus]!
- **See what is coming up.** Selecting a calendar {% term entity %} now lists its upcoming events, instead of only the one in progress. Thanks, [@elupus]!
- **Let your AI assistant read the system log.** AI assistants that use the Home Assistant [LLM] API can now read your [System Log], so they can help you track down problems. Thanks, [@allenporter]!
- **Water heaters and media players in Template.** The [Template] integration can now create water heater and media player entities. Template {% term covers %} can also report and set their speed. Thanks, [@lboue], [@Petro31], and [@Bascht74]!
- **Use trigger variables in template entities.** Trigger-based template entities can now use the variables of their {% term trigger %}. Thanks, [@Petro31]!
- **Fire on anything but one state.** In the [state trigger](/triggers/state/), **From** and **To** gained an **Is not** option, so an {% term automation %} can start when an {% term entity %} changes to any state except the one you pick. Thanks, [@Skaronator]!
- **Clear out several rows at once.** The tables for tags, labels, dashboards, and blueprints gained a selection mode: tick the rows you no longer need and delete them in one go. The Marketplace has it too, for uninstalling. Thanks, [@DaanVervacke]!
- **Easier to use without a mouse.** Data tables can now be operated with the keyboard and read by a screen reader, icon-only badges and tile icons have accessible names, and the thermostat card is labeled for screen readers. Thanks, [@wendevlin], [@timmo001], and [@karwosts]!
- **Choose which clients may connect over HTTPS.** The [HTTP](/integrations/http/) integration lets you pick a <abbr title="Transport Layer Security">TLS</abbr> profile. **Intermediate v6** is the new default and works with almost every browser, app, and device, while **Modern v6** accepts TLS 1.3 only. If your installation still uses an older profile, a repair offers the current one. Thanks, [@Markus98]!
- **More on your Energy dashboard.** You can add your home's total consumption to the [Energy dashboard](/docs/energy/), and the legends of the power and device graphs now show the current value of each source. Thanks, [@Jump-333]!
- **Follow your Thread and Matter networks.** Thread network information moved to a page of its own, and the Matter network map now also shows the {% term devices %} that reach Home Assistant through a bridge. Thanks, [@ovflowd] and [@mib1185]!

### Your AI assistant can help troubleshoot

Home Assistant's <abbr title="Large language model">LLM</abbr> API gives compatible AI assistants tools to search for {% term devices %} and {% term automations %}, review logs, and look up historical statistics. Log access requires an administrator account.

This release goes a step further. An assistant can look up your system information, search the {% term actions %} that are available, and call one. It can list your {% term integrations %} and {% term reload %} one. That makes it something that can act on your setup, not only read it, so give it the access you are comfortable with and no more. You can set the <abbr title="Model Context Protocol">MCP</abbr> server to expose only read-only tools, and an AI conversation can now only be continued by the user who started it.

The [KNX](/integrations/knx/) integration brings an LLM API of its own, with tools for its telegram store, its project file, and its data point types. Any LLM API becomes available only once an administrator attaches it to a conversation agent or to the MCP server.

Thanks, [@balloob], [@allenporter], and [@martinhoefling]!

## Backward-incompatible changes

We do our best to avoid making changes to existing functionality that might unexpectedly impact your Home Assistant installation. Unfortunately, sometimes it is inevitable.

We always make sure to document these changes to make the transition as easy as possible for you. This release has the following backward-incompatible changes:

{% details "AdGuard Home" %}

The **Query log** switch of the AdGuard Home integration now requires AdGuard Home v0.107.30 or newer. On older versions, the switch becomes unavailable.

If AdGuard Home forces HTTPS while the integration is set up without SSL, setup now fails instead of following the redirect to HTTPS. To fix this, remove the integration and add it again with SSL enabled.

Set `alert_color: none` to leave it uncolored.

The card was made for the home and security dashboards, which are not affected. If you added it to a dashboard in {% term YAML %} yourself, update it to the new options.

{% details "Auth" %}

When you reach Home Assistant at an IP address that is not on a local network, such as a public address, a global IPv6 address, or a Tailscale address (`100.64.0.0/10`), the address in your browser now has to match the address Home Assistant sees the request coming in on. Scheme, host, and port all have to match. If they do not, logging in fails with "Invalid client id". Previously, such an address was accepted without that check as soon as it had a port, because of a bug in the check.

Most setups are not affected. Opening Home Assistant directly at such an address keeps working, and so does a reverse proxy that you have set up as a trusted proxy in the [HTTP](/integrations/http/) integration, because Home Assistant then uses the forwarded scheme and host. Domain names and local network IP addresses are accepted the same way as before.

If you do run into "Invalid client id", add your proxy to the trusted proxies of the [HTTP](/integrations/http/) integration, or reach Home Assistant through a domain name.

{% details "Matter" %}

Matter concentration sensors now use the unit the device reports instead of a fixed one. Before, a device measuring in another unit was shown with the wrong unit, for example a <abbr title="total volatile organic compounds">TVOC</abbr> sensor measuring in ppb was shown as ppm.

This affects existing TVOC, carbon monoxide, nitrogen dioxide, and ozone sensors whose device reports a unit other than ppm:

- If the device's unit converts to the old one (for example ppb), the sensor keeps its old unit and the value is now converted, so it changes: a TVOC sensor reporting 189 ppb now shows 0.189 ppm instead of 189 ppm, and the history shows a jump. To get the previous numbers back with the correct unit, set the sensor's unit to the device's unit (here ppb) in its entity settings. Otherwise, update automations, scripts, and templates that use the value. Sensors added from now on use the device's unit directly.
- TVOC sensors reporting µg/m³ or mg/m³ keep their value but switch to the "Volatile organic compounds" device class, which changes their default name (the entity ID stays the same). Their old statistics can't be converted: in **Settings** > **Tools** > **Statistics**, either update the old unit without converting or delete the old statistics.

Matter climate entities now resume their last supported non-off HVAC mode when turned on from Home Assistant, including through dashboard controls and voice commands. For example, an air conditioner turned off while cooling will resume cooling when turned on again. Calling `climate.turn_on` on an entity that is already running now leaves its mode unchanged.

Previously, `climate.turn_on` ignored the previous mode and selected heat/cool, then heat, then cool, depending on what the device supports. Automations or scripts that relied on that behavior should call `climate.set_hvac_mode` with the desired mode instead of `climate.turn_on`.

Devices with a separate power switch, such as Matter room air conditioners, are now switched on by `climate.turn_on`. Previously, Home Assistant only changed the mode, so a device that was switched off stayed off. If the device kept its mode while switched off, only the power is switched on and the mode is left unchanged.

If no previous supported mode is known, the earlier fallback order is still used.

{% details "Watergate" %}

The **Water meter volume** (`sensor.<name>_water_meter_volume`) and **Water meter duration** (`sensor.<name>_water_meter_duration`) sensors of Watergate Sonic now report the _positive_ meter (water flowing in the normal direction) instead of the _positive minus negative_ difference. Entity IDs, unique IDs, and long-term statistics are unchanged.

- **Who is affected:** only devices that have ever recorded reverse flow (backflow). The value steps _up_ once, by the device's lifetime backflow, at the first update after upgrading. Because these sensors are `total_increasing`, Home Assistant records that step as consumption, so the Energy dashboard and statistics show a one-time spike. Devices with no recorded backflow see no change.
- **How to recover:** adjust the spike away with **Adjust a statistic** in {% my developer_statistics title="**Settings** > **Tools** > **Statistics**" %}, or ignore it. Nothing needs to be reconfigured.
- **Why:** the old value silently hid reverse flow and was not the monotonically increasing total the state class promises. The new **Water meter negative volume/duration** sensors expose the reverse reading separately.

On firmware that only reports a single (differential) meter, **Water meter volume/duration** keep reporting that differential and the new negative sensors are unavailable.

Entities for features on non-root endpoints of multi-endpoint Z-Wave devices now live on their own child {% term devices %} of the main device, when the Z-Wave JS device database describes those endpoints as separate parts. Only devices with that information are affected: endpoints that carry a label, or that belong to an endpoint group.

Because the name of an {% term entity %} is built from the device it belongs to, the name of the main device no longer appears in it. A thermostat with three temperature sensors used to be one device with "Air temperature (2)", "Air temperature (3)", and "Air temperature (4)". It is now a main device with one child device per sensor, each named after its endpoint label, such as "Room Sensor", and each with a single "Air temperature" entity. A multi-clamp energy meter becomes the main device plus one child device per clamp.

Entity IDs stay the same, and {% term automations %} and {% term scripts %} that target the main device keep working, because targeting a device also targets the entities of its child devices.

One entity does disappear: the redundant endpoint-2 "slat" value of the Fibaro FGR223 and the Shelly Qubino Wave Shutter (QNSH-001P10) is no longer created. If you had enabled that cover entity, it is gone.
