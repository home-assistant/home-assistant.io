## Welcome to the Marketplace

For years, the community has built {% term "custom integrations" %}, dashboard cards, themes, and templates for Home Assistant. People found them through HACS, the Home Assistant Community Store. With this release, HACS becomes part of Home Assistant as the new [Marketplace](/integrations/marketplace/).

The Marketplace brings the existing HACS experience into Home Assistant and the regular release process. It works with every installation type, including {% term "Home Assistant Container" %}, without manually downloading or unpacking files. Everything in the Marketplace is free, and that will not change.

### Browse and install

You can find the Marketplace under **Settings** > **Marketplace**. It comes with Home Assistant, so there is nothing to set up. As an administrator, you can browse the catalog and install integrations, dashboard cards, themes, and templates. You do not need a GitHub account to install or update projects.

<img src='/images/blog/2026-11/marketplace-settings.webp' alt='Screenshot of the Home Assistant settings page, with a new Marketplace item between Apps and Dashboards, described as: Install integrations, dashboard cards, themes, and templates shared by the community.' class='no-shadow' />

Installing a new {% term integration %} got shorter, too. In HACS, you downloaded it, restarted Home Assistant, went to **Devices & services**, and searched for it again to set it up. In the Marketplace, you select **Install**, and you land straight in its setup flow, without a restart. Updates still need a restart for now.

The page of each project now shows more than its README: how often it was downloaded, its stars on GitHub, and the Home Assistant version it requires, so you know what you're getting into before you install.

<img src='/images/blog/2026-11/marketplace-project.webp' alt='Screenshot of the Marketplace page of the Spook integration, with an Install button, a notice that it is made by the community, and its downloads, stars on GitHub, open issues, and required Home Assistant version.' class='no-shadow' />

Every project you install gets an {% term update "update entity" %}, so updates show up under **Settings** > **Updates**, next to the updates of Home Assistant itself. After an update, a repair tells you when a restart is needed, and can restart Home Assistant for you.

The first time you open the Marketplace, it shows a notice. Everything in the Marketplace is made by the community. It is not tested, audited, or supported by the Home Assistant project, and it runs inside your Home Assistant. Read the notice, select **I understand the risks and agree**, and you're in. Browsing works before that. Installing and updating does not.

<img src='/images/blog/2026-11/marketplace-warning.png' alt='Screenshot of the Marketplace notice, titled Before you install from the Marketplace. It explains that anything you install can connect to the internet, share your data, or slow down Home Assistant, followed by three tips and an I understand the risks and agree checkbox.' />

The Marketplace adds several improvements:

- Group the **Browse** and **Installed** lists by status, type, or source. Home Assistant remembers your grouping.
- Filter by source to distinguish the community catalog from custom repositories.
- Select multiple repositories on the **Installed** tab and uninstall them at once.
- Skipped updates no longer keep a repository at the top of the list or count in the update badge. A new release makes the update available again.
- Search, filters, and sorting are saved in the URL, so you can share a link to a specific Marketplace view.
- Integrations show their brand images before you install them.

<img src='/images/blog/2026-11/marketplace-group-by.png' alt='Screenshot of the Marketplace Browse tab, grouped by status into Installed and Available, with the Group by menu open showing Status, Type, Source, and Don&#39;t group.' />

### Custom repositories

Not every project is in the catalog. To add one that is missing, select **Add from link** and enter its repository URL. The Marketplace then lists it with your other repositories.

The **Custom repositories** page lists repositories you added this way and lets you open or remove them. A repository stays in the list until you uninstall it.

Custom repositories require a GitHub connection. The Marketplace uses GitHub device sign-in, so you approve the connection on GitHub without entering your password in Home Assistant. The connection only reads public information and cannot access private repositories.

### Thank you, HACS

HACS made this possible. [@ludeeus] founded it, and donated it to the Open Home Foundation about a year and a half ago, which is what made bringing it into Home Assistant possible. Together with the HACS maintainers and the many developers publishing their projects, he built the ecosystem that the Marketplace now carries forward. Thank you. ❤️

If you use HACS today, there is nothing you need to do. Home Assistant migrates it when it starts after the update. Everything you installed stays installed and keeps receiving updates, your custom repositories and update entities carry over, and links and bookmarks that point to HACS now open the Marketplace.

The HACS installer stops at Home Assistant 2026.11, so a separate HACS installation is no longer possible on this version. The old HACS won't get new releases either: the Marketplace ships with every Home Assistant update. Everything you need to know about the move, for users and for publishers, is in the [Marketplace documentation](/integrations/marketplace/#coming-from-hacs).

This is a starting point, and the first version of what a marketplace for Home Assistant could become. Got ideas? Share them in the Marketplace section of the [feature request discussions](https://github.com/orgs/home-assistant/discussions) on GitHub. Found a bug? Report it in the Home Assistant issue tracker, not in the HACS repository.

## Exclude items from a target

Targets are a great way to keep your {% term automations %} and {% term scripts %} up to date. Point one at an {% term area %}, a {% term floor %}, or a {% term label %}, and Home Assistant finds the matching {% term entities %} for you, including the ones you add later. There was just one catch: you couldn't leave one out. Turn on all the lights on the ground floor, except the one in the kitchen? Your only option was to list every light yourself, and lose everything that made the target smart in the first place.

You can now exclude entities, devices, areas, floors, and labels from a target. In a {% term trigger %}, {% term condition %}, or {% term action %}, select **Exclude target** next to **Add target**, then choose what to leave out. You can also open a target's details, clear the checkboxes of the items to exclude, and select **Apply**.

<img src='/images/blog/2026-11/exclude-target-details.png' alt='Screenshot of the target details of the Ground floor, with checkboxes to include or exclude each area, device, and entity. The Kitchen Lights are struck through and marked as excluded.' />

Each exclusion is listed below the targets it takes entities out of, with the number of entities it removes. An exclusion that doesn't match anything has no effect, and is listed under **Exclusions with no effect**, where you can remove it.

And exclusions stay as smart as the targets they belong to. Home Assistant works them out every time the trigger, condition, or action runs. Exclude the kitchen, add another light to the kitchen next month, and that light is left out as well. No need to touch the automation again.

This works in triggers, conditions, and actions, in both automations and scripts. If you write {% term YAML %}, add an `exclude` block to the `target`, with the same keys as the target itself. For all the details, including how old-style {% term groups %} behave, refer to [excluding targets](/docs/automation/targets/#excluding-targets).

Thanks, [@jpbede], [@emontnemery], and [@marcinbauer-ohf]! 🙏

The automation editor also has a few improvements:

- **Is not for the state trigger**: Set **From** or **To** to **Is not** to make a {% term trigger %} fire when the state changes to or from any value other than the one you select. No YAML is needed. Thanks, [@Skaronator]!
- **Recently used**: The dialog for adding a trigger, condition, or action now starts with the ones you used recently, including your recently selected targets. Thanks, [@wendevlin]!
- **People in the target picker**: When adding a trigger or condition, find **People** under **Other**, next to **Time** and **Sun**. This makes it easier to create a rule for when someone comes home. Thanks, [@marcinbauer-ohf]!
- **Edit ID is back**: You can set the ID of a trigger from its menu again. Thanks, [@jpbede]!
- **Edit in YAML for choose options**: Edit the options of a choose action in YAML, like other rows. Thanks, [@oneseventhree]!
- **Undo after cutting**: If you cut a trigger, condition, or action by mistake, select **Undo** in the notification to restore it. Thanks, [@marcinbauer-ohf]!

## Name it once, Home Assistant adds the context

Name a thing once, and Home Assistant makes sure it makes sense everywhere. That is the idea behind how {% term entities %} are named from this release on, and it has been more than four years in the making. You give an entity its own name, like "Temperature". Home Assistant knows which device it belongs to, and in which area that device lives, so it can add that context where it helps. By default, that is the name of the device: the "Temperature" of a "Thermostat" in the "Bedroom" shows up as "Thermostat Temperature". Where you want more, a card can add the area too, like "Bedroom Thermostat Temperature".

Naming has been a topic in the community for years, with threads like "How do you name your devices?" and "Naming strategies for entities?", all looking for a system that keeps a growing home readable.

It's time to let those systems go. You shouldn't need a strategy to make sense of the information in Home Assistant. Home Assistant should give you the context you need, at the moment you need it. Now you rename the device, and every entity on it follows. Entities you renamed, and entities you never touched, get their context the same way.

You see this in dashboards, settings, the activity and logbook, the voice assistant settings, and the apps. The same name, in the same structure, everywhere you look.

A few things to know:

- **Renaming an entity** only renames the entity. If you want to change the name of the device, rename the device. For the main entity of a device, which should go by the name of the device, turn on **Use device name** in its settings.
- **Devices with multiple parts**, like a power strip, now get a {% term device %} per part, each with its own name and {% term area %}. These are called child devices. A child device inherits the area of its parent, until you give it one of its own. Integrations are moving to them one by one, starting with the multi-channel switches in Tuya.
- **Your own names are kept.** Home Assistant migrates names you set. If an entity's displayed name changes, the old name remains an alias for voice assistants. For example, "turn on the ceiling light" continues to work.
- **Templates:** The `friendly_name` attribute is planned for deprecation. Use [`entity_name()`](/template-functions/entity_name/), [`device_name()`](/template-functions/device_name/), and [`area_name()`](/template-functions/area_name/) to build the name you need.

What doesn't change: entity IDs. Your {% term automations %}, {% term scripts %}, and dashboards keep working.

We are upfront about one thing: this is a backward-incompatible change. Some names look different after the update, and you notice that most on your dashboards. Cards, badges, and rows without a name now show the device name followed by the entity name, instead of the friendly name. Making them shorter is quick: rename the device or the entity, turn on **Use device name** for the main entity, or set a name on the card. The details are in the [backward-incompatible changes](#backward-incompatible-changes) below.

This is the short version. A separate blog post about entity naming is published on November 2, two days before this release, and tells the full story: [TODO: Title of the entity naming blog post](/blog/2026/11/02/todo-entity-naming-blog-post/).

This project ran for more than four years, and many people worked on it along the way. Thank you to everyone who helped make this happen! 🙏

## Why did that happen?

A light turned on, and nobody touched it. Or an {% term automation %} did something you didn't expect. Finding out why is part of living with a smart home, so this release adds a handful of ways to find the answer faster.

### See what triggered it

The **Activity** panel has a new **Triggered by** filter. Use it to show only what a person did, what your {% term automations %} or {% term scripts %} did, or what an {% term integration %} did, like HomeKit or Google Assistant. Accounts that don't belong to a person, like the one used by Node-RED, count as integrations. Entries without a known cause are listed under **Other**.

Thanks, [@piitaya]!

### Follow a trace into the script it called

When an automation or script runs another script, or triggers an automation, the step in its trace now has a **View trace of** link to exactly that run. Before, you had to find the right run yourself, by timestamp. It works from automation to script, script to script, and automation to automation, for each iteration of a repeat, and for a script that starts itself. The link shows up in the step details and in the trace timeline. The page also keeps the run you are looking at in its address, so going back in your browser takes you back to the previous run.

<img src='/images/blog/2026-11/trace-link.png' alt='Screenshot of the trace of a script named Child A, with the step details of an action that runs the script Child B, and a link: View trace of Child B.' />

Thanks, [@Xyolyp]!

### Live logs for each integration

While debug logging is enabled for an integration, the banner on its page now has a **Show logs** button, next to **Disable**. It opens a dialog with only the log lines of that integration, including the libraries it uses: first what it logged since Home Assistant started, then new lines as they come in. You can search, turn line wrapping on or off, and download what you captured. Handy while you're trying to reproduce an issue, without digging through the full log.

The logs page under {% my logs title="**Settings** > **System** > **Logs**" %} got a filter as well. Select one or more integrations, and the errors list and the raw logs only show their lines. Your search, your filter, and the raw view are kept in the address, so you can bookmark a filtered view or share a link to it.

Thanks, [@erwindouna] and [@timmo001]!

### Remove bad readings from your history

One bad measurement can ruin the graph of a {% term sensor %}. {% term "long-term statistics" "Statistics" %} of values like temperature can't be adjusted, so the only fix was to delete the whole statistic and lose its history. Now you can delete just a time range. In **Tools** > **Statistics**, select the delete option of a statistic, pick the time range, and the dialog previews the data before you delete anything. Everything outside that range stays.

<img src='/images/blog/2026-11/statistics-delete-range.png' alt='Screenshot of the dialog to delete statistics in a time range for Living room Temperature, with a graph showing one spike of bad measurements.' />

Thanks, [@balloob]!

### Every action, on the record

**Tools** has a new **Action history** tab. It lists the {% term actions %} that were called in Home Assistant, with the action, its targets, what caused it, and when. You can search the list and pick a time range. Select an action to see its details: the cause, the user, the context ID, and the data it was called with. Copy that data as {% term YAML %} with one button, and when there is a trace, **View trace** opens it.

<img src='/images/blog/2026-11/action-history.png' alt='Screenshot of the Action history tab in Tools, listing actions with their targets, the cause of each, like By automation: Hallway motion light, and the time.' />

The details of an entry in **Activity** got better too. When an automation calls scripts, each run now links to its own trace. Before, they all opened the same one.

Thanks, [@joostlek] and [@Xyolyp]!

## Cameras Matter

{% term Matter %} keeps growing up. With Matter 1.5, cameras are part of the standard, and Home Assistant now supports them. And while we were at it, cameras got a voice.

### Matter cameras

The [Matter](/integrations/matter/) integration now supports Matter 1.5 cameras. A Matter camera shows up as a camera in Home Assistant, with live video and snapshots. The live video is streamed with <abbr title="Web Real-Time Communication">WebRTC</abbr>, directly between your browser and the camera. The camera {% term entity %} follows the camera, including whether its privacy mode is on.

Matter cameras need a Matter server that is recent enough to support them. Home Assistant only discovers cameras when the connected server does.

Thanks, [@arturpragacz]!

### Talk back through your cameras

Cameras can talk now, too. A new Labs preview feature, **Two-way audio**, adds a talk button to the live stream, so you can talk to whoever is near your camera or doorbell. Turn it on in {% my labs title="**Settings** > **System** > **Labs**" %}.

The talk button appears for cameras that support two-way audio, and whose {% term integration %} has added support for it. In this release, that is Matter cameras and [Reolink](/integrations/reolink/). A Reolink camera needs to use <abbr title="Real-Time Streaming Protocol">RTSP</abbr>, because <abbr title="Real-Time Messaging Protocol">RTMP</abbr> and <abbr title="Flash Video">FLV</abbr> can't carry audio back to the camera.

Browsers only allow microphone access over a secure connection, so for now two-way audio works when you open Home Assistant over HTTPS. We're working on bringing it to the Home Assistant apps over HTTP as well.

Thanks, [@starkillerOG]! And thanks to [@sdb9696] for the earlier work this builds on.

## Store backups and media on local drives

{% term backups "Backups" %} and media take up a lot of space, and the best place for them is often not the drive Home Assistant runs on. Besides network storage, you can now add an internal drive or a USB drive. Go to {% my storage title="**Settings** > **System** > **Storage**" %}, select **Add storage**, and select **Local disk** as the type. Use it for backups, media, or shared files, just like network storage. Home Assistant remembers the disk by its file system identifier, so it keeps working after a restart or when the device name changes, and a repair tells you if the disk is disconnected. The disk needs to be formatted already. For the supported file systems and all the details, refer to the [local disk storage documentation](/common-tasks/os/#local-disk-storage).

Backups got a few more improvements. Restoring no longer makes a temporary copy of the whole backup first, which saves free space and time, especially for backups on network storage. The progress bar on the backup page now follows the upload to Dropbox, Azure Storage, SFTP Storage, Synology DSM, and Backblaze B2. And the new **Last successful automatic backup size** {% term sensor %} lets you keep an eye on how big your automatic backups are, so you can get notified when they suddenly grow or shrink.

Thanks, [@MindFreeze], [@agners], [@KapJI], and [@erwindouna]!

## Reach the far corners with LoRaWAN

<abbr title="Long Range Wide Area Network">LoRaWAN</abbr> is a long-range, low-power wireless protocol, often used for battery-powered sensors in places your Wi-Fi never reaches, like a garden, a shed, or a field. Home Assistant now speaks it. Connect your LoRaWAN network server, [ChirpStack](/integrations/chirpstack/) or [The Things Network](/integrations/thethingsnetwork_lorawan/), and Home Assistant offers the matching device {% term integration %}, like [SenseCAP](/integrations/sensecap_lorawan/), when a supported device shows up.

All of it comes together in a new **LoRaWAN** page in **Settings** > **Connectivity**. It shows your connections and how many devices each has, and a table of all your devices that you can search and filter by connection. A map shows how your network hangs together: which gateways receive which devices, and which devices no gateway has seen. On the page of a device, you find its radio details, like signal strength, the last time it reported in, and its battery. A device that Home Assistant doesn't support yet still shows up, with a note on what is missing. And when you want to add a new device, Home Assistant takes you straight to the management console of its connection.

## Backward-incompatible changes

We do our best to avoid making changes to existing functionality that might unexpectedly impact your Home Assistant installation. Unfortunately, sometimes it is inevitable.

We always make sure to document these changes to make the transition as easy as possible for you. This release has the following backward-incompatible changes:

{% details "AdGuard Home" %}

The AdGuard Home integration now requires AdGuard Home v0.107.30 or newer for the Query log switch; on older versions, that switch becomes unavailable. If AdGuard Home forces HTTPS while the integration is set up without SSL, setting it up fails now, instead of following the redirect to HTTPS: remove the integration and add it again with SSL enabled.

([@frenck] - [#184349]) ([AdGuard Home documentation])

[#184349]: https://github.com/home-assistant/core/pull/184349
[AdGuard Home documentation]: /integrations/adguard/

{% enddetails %}

{% details "Apple iCloud" %}

Completed reminders are no longer fetched by default. The iCloud
integration used to include completed reminders in every Reminders
fetch, which on accounts with a very large history could block startup
for a long time.

To keep the old behavior, enable **Include completed reminders** during
setup or afterward in the integration options under **Settings** >
**Devices & services** > **Apple iCloud** > **Options**.

([@timlaing] - [#186175]) ([Apple iCloud documentation])

[@timlaing]: https://github.com/timlaing
[#186175]: https://github.com/home-assistant/core/pull/186175
[Apple iCloud documentation]: /integrations/icloud/

{% enddetails %}

{% details "Auth" %}

Logging in to Home Assistant through a URL that uses a public IP address with a port, such as `http://203.0.113.10:8123` or `http://[2001:db8::1]:8123`, now fails with "Invalid client id". This also applies to Tailscale addresses (`100.64.0.0/10`). Previously these were accepted because of a bug in the check, while the same address without a port was already rejected.

To keep logging in, access Home Assistant through a domain name (for example, a Tailscale MagicDNS name or your own DNS name) or a local network IP address.

([@elupus] - [#186537]) ([Auth documentation])

[#186537]: https://github.com/home-assistant/core/pull/186537
[Auth documentation]: /integrations/auth/

{% enddetails %}

{% details "Besen" %}

The Besen **Charging status** sensor now reports `scheduled` instead of `canceled` while a scheduled start is pending. Update {% term automations %}, {% term scripts %}, and {% term templates %} that check for `canceled` to use `scheduled`. The old name incorrectly described a pending reservation as canceled.

([@moryoav] - [#186968]) ([Besen documentation])

[@moryoav]: https://github.com/moryoav
[#186968]: https://github.com/home-assistant/core/pull/186968
[Besen documentation]: /integrations/besen/

{% enddetails %}

{% details "Bitcoin" %}

If you set Bitcoin up in {% term "`configuration.yaml`" %}, setup now moves to the UI. On the first restart after this update, Home Assistant reads the `currency` from your YAML and creates the integration for you. Your sensors keep the names and entity IDs they had.

The `display_options` option is no longer supported, so all 21 sensors are
created, even if you previously selected only some of them. This does not add
API requests; all sensors use the same two calls.

Entity IDs created with `entity_namespace` are not preserved. For example,
`sensor.wallet_exchange_rate_1_btc` becomes `sensor.exchange_rate_1_btc`.

([@Nihvel] - [#180515]) ([Bitcoin documentation])

[#180515]: https://github.com/home-assistant/core/pull/180515
[Bitcoin documentation]: /integrations/bitcoin/

{% enddetails %}

{% details "Bluesound" %}

The deprecated `bluesound.join` and `bluesound.unjoin` {% term actions %} have been removed. Update {% term automations %} and {% term scripts %} to use `media_player.join` and `media_player.unjoin`.

([@LouisChrist] - [#184755]) ([Bluesound documentation])

[@LouisChrist]: https://github.com/LouisChrist
[#184755]: https://github.com/home-assistant/core/pull/184755
[Bluesound documentation]: /integrations/bluesound/

{% enddetails %}

{% details "Calendar and Sun" %}

Sun {% term triggers %} (`sun.*`) and the `calendar.event_started` and `calendar.event_ended` triggers used to default to `offset_type: before`, so a positive `offset` fired before the event. The sign of the offset now decides instead: negative fires before the event, positive fires after. If you wrote one of these triggers in {% term YAML %} with an `offset` but without `offset_type`, flip the sign of the offset.
