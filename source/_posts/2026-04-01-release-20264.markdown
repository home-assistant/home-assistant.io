## Infrared becoming a first-class citizen of Home Assistant

This release introduces native infrared support in Home Assistant, opening the door to controlling a _massive_ range of devices that were previously out of reach. Think about all those TVs, air conditioners, fans, sound bars, and other appliances sitting in your home that still rely on their little infrared remote. With this update, Home Assistant can now talk to them. 📡

You might already be familiar with how [Bluetooth proxies](/integrations/bluetooth/) transformed Bluetooth in Home Assistant, making it possible to reach Bluetooth devices anywhere in your home through relatively inexpensive [ESPHome](https://esphome.io) devices. We're doing the same thing for infrared. With the new [Infrared](/integrations/infrared/) integration, Home Assistant now supports infrared proxies: small ESPHome-powered devices with an [IR transmitter](https://esphome.io/components/ir_rf_proxy/) that can send infrared commands on behalf of Home Assistant. This means Home Assistant can now control any device that responds to an infrared remote, as long as there's an {% term integration %} that knows how to speak that device's protocol.

<img src='/images/blog/2026-04/temp-infrared-proxy.png' alt='Screenshot of the Infrared Proxy device page in Home Assistant, showing the Seeed XIAO IR Proxy by Seeed running ESPHome, with its infrared transmitter entity and activity log.' class='no-shadow' />

The first integration to take advantage of this is the [LG Infrared](/integrations/lg_infrared/) integration, which lets you control LG TVs from Home Assistant. It creates a media player entity with support for power, volume, channel control, and playback commands, plus button entities for all the common remote functions like input selection and navigation. Since infrared is one-way by nature, the integration uses assumed states for now, but it works remarkably well for day-to-day use.

<img src='/images/blog/2026-04/temp-lg-tv-infrared-proxy.png' alt='Screenshot of the LG TV device page in Home Assistant, showing media player controls for power, volume, and playback, along with button entities for navigation, HDMI input selection, and other remote functions.' class='no-shadow' />

### Get started in just a few steps

Want to try it out? The quickest way to get started is with the [Seeed Studio XIAO IR Mate](https://www.seeedstudio.com/XIAO-Smart-IR-Mate-p-6492.html). Head over to the ESPHome [Ready-Made Projects](https://esphome.io/projects/?type=irrf) page, connect the device to your computer, and flash it right from your browser. Once it's set up and added to Home Assistant, you'll have a working infrared proxy ready to go. Point it at your LG TV, set up the [LG Infrared integration](/integrations/lg_infrared/), and you're controlling your TV from Home Assistant! 🎉

### Why this matters

This is more than just a fun new feature. Bringing infrared support to Home Assistant aligns with the values of the [Open Home Foundation](https://www.openhomefoundation.org/), and especially _sustainability_. 🌱 There are millions of perfectly good appliances out there that aren't "smart" but do have an infrared receiver. Instead of replacing them with newer connected versions, you can now integrate them into your smart home using a simple, relatively inexpensive IR transmitter. It's a great way to extend the life of existing devices and reduce electronic waste. ♻️

We're excited to see where this goes. The infrared support is designed to work with any IR protocol, and we're looking forward to seeing integrations for more brands and device types. This is just the beginning!

## Purpose-specific automation triggers & conditions

Since [Home Assistant 2025.12](/blog/2025/12/03/release-202512/#purpose-specific-triggers-and-conditions), we've been working on making {% term automation %} building more natural. Instead of thinking in technical terms like {% term entity %} states and numeric thresholds, you can now pick things like "When a light turns on" or "If the climate is heating". Each release since has added more, and this release brings the _biggest batch_ yet.

But this release also brings something fundamentally new to the table: _cross-domain_ triggers and conditions.

### Thinking in real-world concepts, not technical domains

Up until now, every {% term trigger %} and {% term condition %} was tied to a specific entity type. Want to know if a door opened? That depends: is your door sensor a {% term "binary sensor" %}, a {% term cover %} entity, or something else? You had to know the technical difference and pick the right one.

That's not how we think about our homes. You don't think about binary sensors; you think about doors, windows, motion, temperature, and humidity. These are real-world concepts that can be represented by multiple different entity types in Home Assistant.

This release introduces {% term triggers %} and {% term conditions %} that work across entity types and are organized by what they _mean_, not where they live technically. A "door opened" trigger now responds to _any_ door entity, whether it's a contact sensor or a motorized cover. A "temperature changed" trigger picks up readings from temperature sensors, {% term climate %} {% term devices %}, and water heaters alike. You no longer need to know the technical details behind the scenes.

<img src='/images/blog/2026-04/temp-cross-domain-triggers.png' alt='Screenshot of the Add trigger dialog in the automation editor, showing the new cross-domain trigger categories like Humidity, Illuminance, Motion, Occupancy, and Power. The Motion category is selected, revealing Motion cleared and Motion detected triggers.' class='no-shadow' />

And just like the purpose-specific triggers you already know, these new cross-domain triggers and conditions fully support targeting by {% term area %}, {% term floor %}, or {% term label %}. That means you can create a trigger like "When a window on the upstairs floor is opened" without listing every single window. Add a new window sensor up there, and it's automatically included.

### New cross-domain triggers and conditions

The following new triggers and conditions now work across entity types. For each of these, you get both a trigger ("when" something happened) and a condition ("if" something is true), so you can use the same natural concepts throughout your automation:

- **Door**, **garage door**, **gate**, and **window**: trigger when they open or close, and check if they are currently open or closed (from both binary sensors and covers)
- **Motion**: trigger when motion is detected or cleared (across {% term "binary sensor" %} and {% term "event entity" "event entities" %})
- **Occupancy**: trigger when occupancy is detected or cleared, and check if a space is occupied
- **Temperature**: trigger when the temperature changes or crosses a threshold (from temperature sensors, climate devices, and more)
- **Humidity**: trigger when humidity changes or crosses a threshold (from humidity sensors, climate devices, and humidifiers)
- **Illuminance**: trigger when the light level changes or crosses a threshold, and check if it's above or below a value
- **Power**: trigger when power consumption changes or crosses a threshold, and check current values
- **Battery**: trigger when the battery level is low, high, charging, or stopped charging, and check if it's above or below a threshold
- **Air quality**: check for detected pollutants like CO, CO2, smoke, and more
- **Climate**: check if the current or target temperature is above or below a threshold

<img src='/images/blog/2026-04/temp-natrual-automation-example.png' alt='Screenshot of an automation in the visual editor using a cross-domain Motion detected trigger targeted at the Outside area, combined with a Person is not home condition, and actions for recording a camera feed and starting watering.' class='no-shadow' />

### More triggers and conditions for existing domains

On top of the cross-domain additions, a _lot_ of existing {% term domains %} also gained new triggers and conditions:

- **Cover** now has triggers and conditions for all cover types (blinds, shutters, shades, curtains, and awnings)
- **Event entities** now have a generic trigger that fires when any event is received
- **Humidifier** now has a condition to check if the target humidity is above or below a threshold
- **Input boolean** now works with switch triggers (and vice versa), because they behave identically
- **Input text** now works with text triggers, just like text entities
- **Moisture** now has conditions to check if moisture is detected or if a moisture value is above or below a threshold
- **Remote** gained turned on and turned off triggers
- **Schedule** now has conditions to check if a schedule is active
- **Select** gained triggers for when a selection changes
- **Text** now has conditions
- **Water heater** gained both triggers and conditions

### Try it out!

Purpose-specific triggers and conditions are available as a preview feature in {% my labs title="**Home Assistant Labs**" %}. We've been building and refining this for over four releases now, and it's getting really close to being feature complete. If you haven't tried it yet, head over to {% my labs title="**Settings** > **System** > **Labs**" %} to enable it. We'd love your feedback!

## Background color for your dashboard sections

Your dashboard sections can now have a background color! This is a great way to visually group related cards together, make certain sections stand out, or add a personal touch to your dashboard. 🤩

<img src='/images/blog/2026-04/dashboard-sections-background-colors.png' alt='Screenshot showing four dashboard sections: one with no background, one with the default background, one with a gray background at 100% opacity, and one with a red background at 25% opacity.' class='no-shadow' />

To add a background color to a section, open the section settings and turn on the **Background** toggle. From there, you can pick a color from a list of predefined options, or enter a custom hex color code. You can also adjust the opacity to get just the right look.

<img src='/images/blog/2026-04/dashboard-sections-background-color-options.png' alt='Screenshot of the section background settings, showing the background toggle enabled, with a color picker set to red and an opacity slider set to 20%.' class='no-shadow' />

If you have sections side by side on the same row, sections without a background will automatically align with those that have one, keeping everything looking clean and tidy.

## Entity naming: consistent names everywhere

When an {% term integration %} names an {% term entity %}, the full name is composed as {% term device %} name + entity name. For example, a "Motion Sensor" device with a "Temperature" entity becomes "Motion Sensor Temperature." But when _you_ renamed that entity, say to "Ambient temp," the device name was dropped. The friendly name became just "Ambient temp." Two different behaviors for the same thing, depending on who set the name.

This inconsistency has been one of the most common sources of confusion in Home Assistant, and one of the most frequently discussed topics in our community. Starting with this release, we've made this consistent. Entity names now always include the device name as context, whether the name was set by an integration or by you. Renaming that entity to "Ambient temp" will now produce "Motion Sensor Ambient temp," just as the system would for integration-provided names.

<img src='/images/blog/2026-04/temp-rename-entity-setting.png' alt='Screenshot of the entity settings dialog on the Arc reactor device page, showing the Name field set to Temperature. The breadcrumb above shows Garage > Arc reactor, and the entity ID is sensor.arc_reactor_temperature.' class='no-shadow' />

### You should not have to think about naming conventions

One of the most common community questions has always been: "What's your naming convention?" or "How do you name your devices?" You shouldn't have to care about this. Just give your devices and entities the simplest, most natural name, and the UI will automatically adapt to display the right context so you can recognize them everywhere.

In [2025.4](/blog/2025/04/02/release-20254/), we started adding more context to the entity dialogs, showing you which device and {% term area %} an entity belongs to. In [2025.5](/blog/2025/05/07/release-20255/#picking-entities), we updated the entity pickers to show device and area context, gradually eliminating the need to include location information in entity names. And in [2025.11](/blog/2025/11/05/release-202511/#flexible-entity-naming-on-dashboard-cards), we added [flexible name composition controls](/dashboards/naming/) to dashboard cards, letting you choose exactly how names appear: entity only, device, area, floor, or any combination.

<img src='/images/blog/2026-04/temp-entity-picker-provides-context.png' alt='Screenshot of the tile card configuration dialog with the entity picker open, searching for temp. Each result shows the entity name with area and device context underneath, like Temperature with Garage > Arc reactor.' class='no-shadow' />

On a device page, for example, you already know which device you're looking at and which area it's in, so there's no need to repeat the device name on each entity listed there. In an entity picker, you see the full composed name with device and area context. On a dashboard card, you choose what level of detail makes sense. The system handles the context for you, so you don't have to bake it into the name itself.

### This is a backward-incompatible change

We want to be upfront: this will affect some of you.

If you previously renamed entities without including the device name, those entities will now show the device name again in places that use the friendly name (`friendly_name`) attribute, like the logbook and external tools (for example, external voice assistants such as Amazon Alexa, or monitoring tools like Prometheus). The Home Assistant UI is also affected: as the default display on dashboard cards uses the device + entity name, cards showing entities you've renamed will look different. Since [2025.11](/blog/2025/11/05/release-202511/#flexible-entity-naming-on-dashboard-cards), every dashboard card supports [name composition controls](/dashboards/naming/), so you can adjust individual cards to pick the name combination that works best for you.

<img src='/images/blog/2026-04/temp-tile-card-configuration-name-composing.png' alt='Screenshot of the tile card configuration dialog showing the name composition settings under Content. Entity and Area chips are selected, with Device and Floor available as additional options.' class='no-shadow' />

### Migration and voice aliases

To make this transition as smooth as possible, a one-time automatic migration runs when you update to 2026.4 or later. If your custom entity name already starts with the device name (for example, you manually set it to "Motion Sensor Temperature"), the migration strips the duplicate prefix so you don't end up with "Motion Sensor Motion Sensor Temperature." If your custom name doesn't match the device name at all, the old full name is preserved as an Assist voice alias so your voice commands continue to work. This matters because Assist is strict about matching the exact name you use, so preserving those aliases ensures nothing breaks when you talk to your home.

Additionally, you can now disable the automatically generated full entity name from being used as a voice alias. This gives you full control over your voice setup: set your own aliases, and tell the system not to use the generated name if it doesn't work for you.

### Why we're doing this

We know naming changes are never fun, and we know some of you have spent significant time customizing entity names to get things just right. We don't take that lightly.

But the current inconsistency creates real problems that go beyond just how names look in the UI. External systems, databases, companion apps, and especially voice assistants all depend on the friendly name (`friendly_name`) to identify entities. When a user rename drops the device context, those systems lose the ability to tell "Temperature" in the kitchen apart from "Temperature" in the bedroom.

This approach also doesn't scale. With systems now commonly running 1,000 or 2,000+ entities, having a per-entity toggle on naming behavior would add complexity without solving the underlying problem. The system needs to be consistent so it can do the heavy lifting for you, rather than requiring you to manage naming conventions across hundreds of entities.

This change is part of a plan that has been in the works since [July 2022](https://developers.home-assistant.io/blog/2022/07/10/entity_naming/), when we introduced a new entity naming model. The goal has always been to separate device names from entity names and let the system compose the right display name based on context.

Since 2022, our developer community has gradually updated and migrated nearly every single integration in Home Assistant. Every entity provided for any device, across all integrations, needed adjustments for this new model. It is a mandatory [Bronze-tier requirement](/docs/quality_scale/) in our [Integration Quality Scale](https://developers.home-assistant.io/docs/core/integration-quality-scale/), meaning no new integration can be added to Home Assistant without supporting it. That is a massive effort, and we want to give a huge shout-out to all the contributors who helped make this happen over the past four years.

The frontend side of that work has been shipping across many releases. This release brings the backend in line. With this change, users can now edit the entity name directly instead of the composed old friendly name. The companion apps for Android and iOS will also be adopting these changes, so that the same consistent naming experience extends to your phone, tablet, widgets, and watch complications.

It won't be completely painless for everyone, but we believe it's the right step toward making entity naming something that just works, so you can spend your time building out your actual smart home instead of managing naming conventions.

## Matter lock manager

If you have a Matter-compatible smart lock, you can now manage your lock users and PIN codes directly from Home Assistant! 🔐

<img src='/images/blog/2026-04/matter-manage-lock-credentials.png' alt='Screenshot of the Matter lock management dialog showing a list of configured lock users and their credentials.' class='no-shadow' />

On the device page of your Matter lock, you'll find a new **Manage lock** option. It opens a dialog where you can see all configured users, add new ones, edit existing ones, or remove them. When adding a new user, you give them a name, set a PIN code, and choose an access type: full access (can lock and unlock anytime) or one-time access (the code works once and is then automatically deleted by the lock).

<img src='/images/blog/2026-04/matter-manage-lock-add-user.png' alt='Screenshot of the add user dialog with fields for name, PIN code, and access type.' class='no-shadow' />

Under the hood, this is powered by a new set of {% term Matter %} lock {% term actions %} that are also available for use in your {% term automations %} and {% term scripts %}. You can, for example, create a one-time PIN code for a guest and send it in a notification, all from an automation! The available actions include creating and removing users, setting and clearing credentials (like PIN codes and <abbr title="radio-frequency identification">RFID</abbr> tags), and querying the lock's capabilities.

## Backward-incompatible changes

We do our best to avoid making changes to existing functionality that might unexpectedly impact your Home Assistant installation. Unfortunately, sometimes it is inevitable.

We always make sure to document these changes to make the transition as easy as possible for you. This release has the following backward-incompatible changes:

{% details "Entity naming" %}

The entity `friendly_name` attribute is now always prefixed with the device name, even when the entity has been manually renamed by you. This makes the behavior consistent: previously, only integration-assigned names included the device name prefix, while user-given names did not.

A storage migration handles existing entities: names that already include the device name as a prefix are stripped to avoid duplication, while names that don't match the device name are preserved as an explicit alias for backward compatibility with voice assistants.

([@arturpragacz] - [#162763])

[@arturpragacz]: https://github.com/arturpragacz
[#162763]: https://github.com/home-assistant/core/pull/162763

{% enddetails %}

{% details "JVC Projector" %}

The **Picture Mode** and **HDR Processing** entities have been migrated from the sensor domain to the select domain, because they represent selectable settings rather than read-only values.

New entities:

- `select.jvc_projector_picture_mode`
- `select.jvc_projector_hdr_processing`

The legacy sensor entities are now deprecated. If a deprecated sensor is disabled and not referenced by automations or scripts, Home Assistant will remove it from the entity registry. If usage is detected, Home Assistant keeps it and shows a repair issue to help you migrate. Update your automations, scripts, dashboards, and templates to use the new select entities.

([@SteveEasley] - [#165194]) ([JVC Projector documentation])

[@SteveEasley]: https://github.com/SteveEasley
[#165194]: https://github.com/home-assistant/core/pull/165194
[JVC Projector documentation]: /integrations/jvc_projector/

{% enddetails %}

{% details "Litter-Robot" %}

The deprecated night light mode switch entity for Litter-Robot 4 devices has been removed. This switch was replaced by a select entity in Home Assistant 2025.10. If you still use the old switch entity in your automations or scripts, update them to use the select entity instead.

([@natekspencer] - [#165636]) ([Litter-Robot documentation])

[@natekspencer]: https://github.com/natekspencer
[#165636]: https://github.com/home-assistant/core/pull/165636
[Litter-Robot documentation]: /integrations/litterrobot/

{% enddetails %}

{% details "Motion Blinds" %}

On devices that support tilt but do not report a tilt position, the tilt open and tilt close operations now send jog up and jog down commands instead of setting the tilt angle to 0° or 180°. Setting an absolute tilt position usually didn't work on these devices anyway, and jog commands provide a meaningful small step in the intended direction.

If you have automations that rely on the previous tilt behavior for these devices, you may need to adjust them.

([@tobiaswaldvogel] - [#164694]) ([Motion Blinds documentation])

[@tobiaswaldvogel]: https://github.com/tobiaswaldvogel
[#164694]: https://github.com/home-assistant/core/pull/164694
[Motion Blinds documentation]: /integrations/motion_blinds/

{% enddetails %}

{% details "MQTT" %}

Support for the `object_id` option has been removed after 6 months of deprecation. This option was used to suggest the entity ID for an MQTT entity and has been replaced by the `default_entity_id` configuration option.

If you used `object_id` in your MQTT YAML configuration, you were previously asked via a repair flow to update your configuration. If `object_id` is still part of a discovery message, the option will simply be ignored and will not break discovery.

([@jbouwh] - [#164460]) ([MQTT documentation])
