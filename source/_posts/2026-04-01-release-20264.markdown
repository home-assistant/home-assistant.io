It's been a _massive_ effort, touching nearly every single integration, and this release finally brings the backend in line with the frontend work that's been shipping over the past year. It's not the flashiest feature, but it's the kind of foundational work that makes everything else better. 🧱

## Background color for your dashboard sections

Your dashboard sections can now have a background color! This is a great way to visually group related cards together, make certain sections stand out, or simply add a personal touch to your dashboard 🤩

<img src='/images/blog/2026-04/dashboard-sections-background-colors.png' alt='Screenshot showing four dashboard sections: one with no background, one with the default background, one with a grey background at 100% opacity, and one with a red background at 25% opacity.' class='no-shadow' />

To add a background color to a section, open the section settings and turn on the **Background** toggle. From there, you can pick a color from a list of predefined options, or enter a custom hex color code. You can also adjust the opacity to get just the right look.

<img src='/images/blog/2026-04/dashboard-sections-background-color-options.png' alt='Screenshot of the section background settings, showing the background toggle enabled, with a color picker set to red and an opacity slider set to 20%.' class='no-shadow' />

If you have sections side by side on the same row, sections without a background will automatically align with those that have one, keeping everything looking clean and tidy.

### Entity naming: consistent names everywhere

Have you ever renamed an entity to something like "Ceiling Light," only to find that voice assistants, logbook entries, and external tools suddenly lost all context about which room or device it belongs to? Or maybe you've been on the other side of this: you carefully named your device "Living Room Lamp" and its entity "Temperature," and everything worked great... until you renamed the entity, and suddenly the device context just vanished?

This inconsistency has been one of the longest-standing pain points in Home Assistant. When an integration names an entity, the full name is composed as device name + entity name (for example, "Living Room Lamp Temperature"). But when _you_ renamed that entity, the device name was dropped entirely, and only your given name was used. Two different behaviors for the same thing, depending on who set the name.

Starting with this release, we've made this consistent. Entity names now always include the device name as context, whether the name was set by an integration or by you. If your device is called "Living Room Lamp" and you name the entity "Temperature," the full name will be "Living Room Lamp Temperature," regardless of how that name got there.

### What this means for your daily use

This is a **backward-incompatible change**, and we want to be upfront about that.

If you've previously renamed entities and deliberately left out the device name, those entities will now show the device name again in places that use the full `friendly_name` attribute, like the logbook and external tools.

However, here's the important part: **most of what you see in the Home Assistant UI is not affected.** If you've been following along with recent releases, you've actually already been using the new naming system without realizing it.

In [2025.4](/blog/2025/04/02/release-20254/), we started adding more context to the entity dialogs, showing you which device and area an entity belongs to. In [2025.5](/blog/2025/05/07/release-20255/#picking-entities), we updated the entity pickers to show device and area context, gradually eliminating the need to include location information in entity names. And in [2025.11](/blog/2025/11/05/release-202511/#flexible-entity-naming-on-dashboard-cards), we added [flexible name composition controls](/dashboards/naming/) to dashboard cards, letting you choose exactly how names appear: entity only, device, area, floor, or any combination. Those controls already use the structured name components from the entity and device registries, not the `friendly_name` attribute.

So if you're thinking, "Won't all my dashboard cards suddenly show ridiculously long names?" the answer is: no. The frontend already handles this intelligently and has been doing so for quite a while. On a device page, for example, you already know which device you're looking at and which area it's in, so there's no need to repeat the device name over and over again on each entity listed on that page. The system already takes care of that for you.

### The migration

To make this transition as smooth as possible, we've built a one-time automatic migration that runs when you update.

If your custom entity name already starts with the device name (for example, you manually set it to "Living Room Lamp Temperature"), the migration strips the duplicate prefix so you don't end up with "Living Room Lamp Living Room Lamp Temperature."

If your custom name doesn't match the device name at all, the old full name is preserved as a voice alias. This means your voice assistant setups won't break. If you've been calling a light "Bedside Lamp" through Assist or Google Assistant, that still works because it's been carried over as an alias.

### Unified voice name resolution

Speaking of voice, this release also unifies how entity names are resolved across all voice platforms. Previously, Assist, LLMs, and Google Assistant each had their own logic for figuring out what to call an entity. Now they all use the entity registry as the single source of truth. This means more consistent behavior no matter how you control your home by voice.

Additionally, you can now disable the automatically generated full entity name from being used as a voice alias. This gives you full control over your voice setup: set your own aliases, and tell the system not to use the generated name if it doesn't work for you.

### Why we're doing this

We know naming changes are never fun, and we know some of you have spent significant time customizing entity names to get things just right. We don't take that lightly.

But the current inconsistency creates real problems that go beyond just how names look in the UI. External systems, databases, companion apps, and especially voice assistants all depend on `friendly_name` to identify entities. When a user rename drops the device context, those systems lose the ability to tell "Temperature" in the kitchen apart from "Temperature" in the bedroom.

This approach also doesn't scale. With systems now commonly running 1,000 or 2,000+ entities, having a per-entity toggle on naming behavior would add complexity without solving the underlying problem. The system needs to be consistent so it can do the heavy lifting for you, rather than requiring you to manage naming conventions across hundreds of entities.

This change is part of a plan that has been in the works since [July 2022](https://developers.home-assistant.io/blog/2022/07/10/entity_naming/), when we introduced a new entity naming model. The goal has always been to separate device names from entity names and let the system compose the right display name based on where you're looking. On a device page, you see just the entity name. In an entity picker, you see the full composed name with device and area context. On a dashboard card, you choose what level of context makes sense.

Since 2022, our developer community has gradually updated and migrated nearly every single integration in Home Assistant. Every entity provided for any device, across all integrations, needed adjustments for this new model. It is now a mandatory [Bronze-tier requirement](/docs/quality_scale/) in our [Integration Quality Scale](https://developers.home-assistant.io/docs/core/integration-quality-scale/), meaning no new integration can be added to Home Assistant without supporting it. That is a massive effort, and we want to give a huge shout-out to all the contributors who helped make this happen over the past four years.

The frontend side of that work has been shipping across many releases. This release brings the backend in line, making it a prerequisite for future improvements like editing entity names directly (instead of the composed `friendly_name`). The companion apps for Android and iOS will also be adopting these changes, so that the same consistent naming experience extends to your phone, tablet, widgets, and watch complications.

It won't be completely painless for everyone, but we believe it's the right step toward making entity naming something that just works, so you can spend your time building out your actual smart home instead of managing naming conventions.

## Matter lock manager

If you have a Matter-compatible smart lock, you can now manage your lock users and PIN codes directly from Home Assistant! 🔐

<img src='/images/blog/2026-04/matter-manage-lock-credentials.png' alt='Screenshot of the Matter lock management dialog showing a list of configured lock users and their credentials.' class='no-shadow' />

On the device page of your Matter lock, you'll find a new **Manage lock** option. It opens a dialog where you can see all configured users, add new ones, edit existing ones, or remove them. When adding a new user, you give them a name, set a PIN code, and choose an access type: full access (can lock and unlock anytime) or one-time access (the code works once and is then automatically deleted by the lock).

<img src='/images/blog/2026-04/matter-manage-lock-add-user.png' alt='Screenshot of the add user dialog with fields for name, PIN code, and access type.' class='no-shadow' />

Under the hood, this is powered by a new set of Matter lock actions that are also available for use in your automations and scripts. You can, for example, create a one-time PIN code for a guest and send it in a notification, all from an automation! The available actions include creating and removing users, setting and clearing credentials (like PIN codes and RFID tags), and querying the lock's capabilities.

Thanks, [@Ahbrown41], for this awesome contribution! 🙌

### What is an AI-powered assist thinking?

If you use an <abbr title="Large Language Model">LLM</abbr>-powered conversation agent with Assist, you may have wondered what's going on behind the scenes when it's processing your request. Now you can find out! The Assist dialog now shows you the thinking steps and tool calls your AI agent makes while working on your request.

<img src='/images/blog/2026-04/temp-ai-conversation-thinking.png' alt='Screenshot of the Assist dialog showing an expanded Show details section with the AI agent thinking steps and tool calls.' class='no-shadow' />

Expand it to see the agent's reasoning process, which tools it called, what arguments it passed, and what results it got back. This is great for understanding how your AI agent arrives at its answers, and super helpful when debugging automations or tweaking your agent's behavior.

## Backward-incompatible changes

We do our best to avoid making changes to existing functionality that might unexpectedly impact your Home Assistant installation. Unfortunately, sometimes it is inevitable.

We always make sure to document these changes to make the transition as easy as possible for you. This release has the following backward-incompatible changes:

{% details "Entity naming" %}

The entity `friendly_name` attribute is now always prefixed with the device name, even when the entity has been manually renamed by you. This makes the behavior consistent: previously, only integration-assigned names included the device name prefix, while user-given names did not.

A storage migration handles existing entities: names that already include the device name as a prefix are stripped to avoid duplication, while names that don't match the device name are preserved as an explicit alias for backward compatibility with voice assistants.

([@arturpragacz] - [#162763])

[@arturpragacz]: https://github.com/arturpragacz
[#162763]: https://github.com/home-assistant/core/pull/162763

{% enddetails %}

{% details "JVC Projector" %}

The **Picture Mode** and **HDR Processing** entities have been migrated from the sensor domain to the select domain, because they represent selectable settings rather than read-only values.

New entities:

- `select.jvc_projector_picture_mode`
- `select.jvc_projector_hdr_processing`

The legacy sensor entities are now deprecated. If a deprecated sensor is disabled and not referenced by automations or scripts, Home Assistant will remove it from the entity registry. If usage is detected, Home Assistant keeps it and shows a repair issue to help you migrate. Update your automations, scripts, dashboards, and templates to use the new select entities.

([@SteveEasley] - [#165194]) ([JVC Projector documentation])

[@SteveEasley]: https://github.com/SteveEasley
[#165194]: https://github.com/home-assistant/core/pull/165194
[JVC Projector documentation]: /integrations/jvc_projector/

{% enddetails %}

{% details "Litter-Robot" %}

The deprecated night light mode switch entity for Litter-Robot 4 devices has been removed. This switch was replaced by a select entity in Home Assistant 2025.10. If you still use the old switch entity in your automations or scripts, update them to use the select entity instead.

([@natekspencer] - [#165636]) ([Litter-Robot documentation])

[@natekspencer]: https://github.com/natekspencer
[#165636]: https://github.com/home-assistant/core/pull/165636
[Litter-Robot documentation]: /integrations/litterrobot/

{% enddetails %}

{% details "Motion Blinds" %}

On devices that support tilt but do not report a tilt position, the tilt open and tilt close operations now send jog up and jog down commands instead of setting the tilt angle to 0° or 180°. Setting an absolute tilt position usually didn't work on these devices anyway, and jog commands provide a meaningful small step in the intended direction.

If you have automations that rely on the previous tilt behavior for these devices, you may need to adjust them.

{% enddetails %}

{% details "MQTT" %}

Support for the `object_id` option has been removed after 6 months of deprecation. This option was used to suggest the entity ID for an MQTT entity and has been replaced by the `default_entity_id` configuration option.

If you used `object_id` in your MQTT YAML configuration, you were previously asked via a repair flow to update your configuration. If `object_id` is still part of a discovery message, the option will simply be ignored and will not break discovery.

[#164460]: https://github.com/home-assistant/core/pull/164460
[MQTT documentation]: /integrations/mqtt/

{% enddetails %}

{% details "pyLoad" %}

pyLoad 0.4.x is now [deprecated](https://github.com/pyload/pyload/releases/tag/v0.4.x) and users are advised to switch to pyLoad-ng 0.5.0. pyLoad-ng introduced a new API, and support for the old API has been dropped.

[@tr4nt0r]: https://github.com/tr4nt0r
[#164495]: https://github.com/home-assistant/core/pull/164495
[pyLoad documentation]: /integrations/pyload/

{% enddetails %}

{% details "Tuya" %}

Previously deprecated switch entities used to control valves have been removed. Use the valve entities instead. If you have automations or scripts that reference these switch entities, update them to use the corresponding valve entities.

([@epenet] - [#164657]) ([Tuya documentation])

[@epenet]: https://github.com/epenet
[#164657]: https://github.com/home-assistant/core/pull/164657
[Tuya documentation]: /integrations/tuya/

{% enddetails %}

{% details "Z-Wave" %}

The Z-Wave Installer panel has been removed. This panel was hidden and required an undocumented YAML configuration to enable. The same functionality is now natively available through Z-Wave JS UI in the Z-Wave add-on.
